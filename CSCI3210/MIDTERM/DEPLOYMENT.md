# Put Pixel War on GitHub Pages + Render

The code is prepared for this layout:

- Your portfolio stays at **https://nathanielgreisen.github.io/**.
- Its **MIDTERM** link opens **https://nathanielgreisen.github.io/CSCI3210/MIDTERM/**.
- GitHub Pages serves the built React app. Render runs Django, PostgreSQL, and Redis-compatible Key Value.

**You do not need a Render API key.** Connect Render to GitHub during account setup. The only value you must copy between the dashboards is the public address of your Render web service.

Nothing is deployed just by saving these files locally. Push the changes, create the Render resources, and enable the Pages workflow using the steps below.

## 1. Review the free plans

The repository's root `render.yaml` selects **free** for the web service, database, and Key Value. The free Hobby workspace and the individual service plans are different settings. Review the resource list before confirming creation; it should show free plans for all three resources.

These are demo plans:

- The web service sleeps after inactivity. The first visitor may wait about a minute while it wakes up. The frontend waits longer for requests and reconnects automatically.
- **Free Render PostgreSQL expires 30 days after creation.** Plan to export your data, upgrade, or move databases before that deadline. Your free workspace does not prevent database expiration.
- Free Key Value can lose its contents on restart. The drawing and cooldown times are saved in PostgreSQL, so the app can rebuild its cache.

These limits are documented in [Render's free-plan guide](https://render.com/docs/free). The Blueprint format is documented in [Render's Blueprint reference](https://render.com/docs/blueprint-spec).

## 2. Push the prepared code

In VS Code, open a terminal at the repository root (`nathanielgreisen.github.io`). Read `git status` and your diff before committing. Keep your recent title changes; the deployment changes preserve them.

```bash
git status --short
git diff
```

Commit the deployment files and changed app files, then push to `main`. In particular, include:

- `.github/workflows/pages.yml`
- `scripts/build_pages.py`
- `render.yaml`
- `.gitignore` and the root `index.html`
- This deployment guide
- The changed backend and frontend source/configuration files, dependency lock file, and `.env.example` templates

Do **not** add your real `.env`, `.venv`, database, `node_modules`, `dist`, `staticfiles`, or `_site`. Ignore rules exclude these. The build creates public output automatically.

## 3. Create the backend in Render

1. Sign into Render and connect your GitHub account. Grant access to this repository.
2. Choose **New → Blueprint** and select **nathanielgreisen.github.io**.
3. Use the **main** branch and the root **render.yaml** file. Review the proposed resources:
   - `pixel-war-api` — Python web service
   - `pixel-war-db` — PostgreSQL database
   - `pixel-war-cache` — Key Value service
4. Confirm the free plans, then create the Blueprint. Keep the resources in the same region; the file uses Oregon.
5. Wait until the database/cache are available and the web deployment succeeds. The web service installs packages, collects admin CSS, creates database tables, and seeds canvas 1 automatically. Initial setup can take several minutes.
6. Open **pixel-war-api** and copy its public URL from the dashboard. It will resemble `https://pixel-war-api-xxxx.onrender.com`. The exact name may differ; always use the URL Render shows you.
7. Open that URL with **`/health/`** appended. You should get:

```json
{"status":"ok","service":"pixel-war"}
```

8. Also open **`/api/canvases/1/snapshot/`** on that same service. You should see JSON with canvas dimensions, version, and pixels. This second check verifies database/cache access as well as the running web server.

The backend root `/` may return 404. That is expected: visitors use the GitHub Pages frontend, and Django exposes `/admin/`, `/api/`, and `/health/`.

### Where the Render settings go

Open **Render → pixel-war-api → Environment** to inspect or change these. The Blueprint supplies the required values automatically:

| Name | Value/source | Is it secret? |
|---|---|---|
| `DJANGO_SECRET_KEY` | Generated by Render; leave the generated value in place | **Yes** |
| `DATABASE_URL` | Internal connection URL from `pixel-war-db` | **Yes** |
| `REDIS_URL` | Internal connection URL from `pixel-war-cache` | **Yes** |
| `FRONTEND_ORIGINS` | `https://nathanielgreisen.github.io` | No |
| `DJANGO_DEBUG` | `0` | No |
| `PYTHON_VERSION` | Set in the Blueprint | No |

Render supplies `RENDER_EXTERNAL_HOSTNAME` and `PORT` itself. You do not need to enter them. Django adds that hostname to its allowed hosts automatically. Use just the origin for `FRONTEND_ORIGINS`: no `/CSCI3210/MIDTERM/` path and no trailing slash. For a future custom domain, add its HTTPS origin to this comma-separated list too.

If you create the resources manually instead of using the Blueprint, the backend root directory is `CSCI3210/MIDTERM/pixel-war/backend`, build command is `bash build.sh`, start command is `bash start.sh`, and health path is `/health/`. Manually copy the **internal** Postgres and Key Value URLs into the corresponding environment variables. The Blueprint handles those connections for you.

**Do not put any of these secrets into GitHub Pages, frontend source, a `VITE_` variable, or a committed `.env`.** Anything built into browser JavaScript is public.

## 4. Give GitHub the public backend URL

1. Open your GitHub repository.
2. Go to **Settings → Secrets and variables → Actions**.
3. Choose the **Variables** tab, then **New repository variable**.
4. Enter:
   - **Name:** `VITE_BACKEND_URL`
   - **Value:** your complete public Render URL, such as `https://pixel-war-api-xxxx.onrender.com`
5. Save it.

Use the web service URL, **not** a database URL, API key, admin password, or deploy hook. Do not include `/api/`, `/health/`, `/ws/`, or another path. The frontend appends the appropriate paths and derives `wss://` for the socket.

This is intentionally a **repository variable**, not a secret: the browser must know where the server is. Vite reads it when the app is built. Changing the variable requires another Pages build; refreshing the browser alone does not rebuild the app.

For a manual production build on your computer, copy `frontend/.env.production.example` to `frontend/.env.production.local`, replace the example with your actual public URL, and run `npm run build` inside `frontend/`. This is optional; GitHub Actions handles the build in the normal setup.

## 5. Enable the GitHub Pages build

1. In the same repository, open **Settings → Pages**.
2. Under **Build and deployment → Source**, select **GitHub Actions**. This replaces the previous “Deploy from a branch” publishing process; it does not delete your repository or portfolio files.
3. Open **Actions → Deploy portfolio and Pixel War to GitHub Pages**.
4. Choose **Run workflow**, select **main**, and run it. If GitHub asks to enable Actions, enable it for this repository.
5. Wait for both build and deploy jobs to finish successfully.
6. Visit your homepage, expand the Web Application Development section, and select **MIDTERM**.

Future pushes to `main` rebuild and publish the portfolio automatically. Render also deploys changes to its backend directory from the connected repository. If you only change `VITE_BACKEND_URL`, run the Pages workflow manually again.

The workflow builds React at `/CSCI3210/MIDTERM/` and assembles your existing public portfolio pages/assets into `_site`. It uploads that assembled folder, not the whole working directory. Backend Python files, local environments, source secrets, and Python databases are excluded from the Pages artifact. The build also creates `.nojekyll` so the compiled files are served directly. See [GitHub's custom Pages workflow documentation](https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages).

If you deploy Pages before setting `VITE_BACKEND_URL`, the rest of the portfolio still works. MIDTERM displays a “not connected” message until you set the variable and rebuild, instead of trying to send API requests to GitHub Pages.

## 6. Accounts, admin, and existing local data

The hosted PostgreSQL database starts empty. Your local SQLite file and existing local accounts are unchanged, but they are **not copied to Render**. Register new demo accounts on the hosted app. If you want the existing local drawing/accounts transferred, do that as a separate data-migration step rather than uploading SQLite publicly.

Free Render web services do not include an interactive shell. To optionally create a hosted administrator without shell access:

1. Open **Render → pixel-war-api → Environment**.
2. Add `DJANGO_SUPERUSER_USERNAME` with the admin username you want.
3. Add `DJANGO_SUPERUSER_PASSWORD` with a strong password. This is a **secret**; enter it only in Render.
4. Save the environment changes and redeploy/restart the service.
5. Startup creates that account before serving requests. It does not change an existing admin's password or promote an existing ordinary account. If the username is taken by an ordinary account, choose a different one.
6. Visit **your Render service URL + `/admin/`** and sign in.
7. Remove **both** bootstrap variables from Render after account creation. The account remains saved in PostgreSQL.

You do not need a hosted admin just to register, sign in, draw pixels, or view history. An admin is useful for assigning canvas moderators. Do not expose bootstrap passwords through GitHub Actions or the frontend.

## 7. Verify the public app

Keep your local servers stopped during this check so you know the deployment is independent of your laptop:

1. Open the GitHub Pages MIDTERM link in a normal window and a private window.
2. Let the free Render service wake up if necessary.
3. Register/sign in with two accounts and place a pixel. It should appear in both windows immediately.
4. Attempt a second placement before the cooldown ends; it should be rejected/count down.
5. Refresh the page, sign back in, and confirm the drawing remains.
6. Check zoom/pan and refresh the placement history.
7. Verify the homepage and existing homework links still load.

If it says **not connected**, check the GitHub repository variable and rerun Pages. If the browser reports **CORS**, check `FRONTEND_ORIGINS` in Render. If pixels load but the socket remains offline, check the browser's Network → WS tab and Render logs; the socket must point to the Render domain with `wss://`, not `github.io`.

If registration/loading times out on the first visit, wait for the Render service to finish waking up, then retry. A failed initial metadata request is retried when the canvas connection becomes ready. If requests start returning 503 after weeks of working, check whether the free database has expired.

## Local development still works

Your normal `npm run dev` uses the existing Vite `/api` and `/ws` proxies to Django on port 8000. No Render key or URL is needed locally. Keep your existing private backend `.env` and local SQLite file. The new `.env.example` is a template, not a replacement for your real settings.
